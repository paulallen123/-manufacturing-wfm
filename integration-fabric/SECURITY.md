# Integration security boundary

The integration fabric is intentionally safer than a generic "connect to anything" proxy.

- **No arbitrary URL probing.** Public probes may only use URLs already committed to the reviewed registry.
- **No credentials in Git.** OAuth secrets, API keys, passwords, client certificates and tenant tokens belong at the executor boundary.
- **Read-only first.** `writeEnabled` is false across the registry. Writes are enabled per connector only after sandbox evidence, idempotency/replay controls and customer authorisation.
- **High-privilege API tokens need an extra boundary.** A vendor API token must not be treated as least privilege merely because WFM intends to issue GET requests. If a token can also reach mutative configuration, tag, project, device or control routes, terminate it behind a customer-side read facade, restricted projection/service account, API gateway or equivalent policy enforcement before exposing it to the WFM connector.
- **Super-admin credentials are forbidden in the normal connector plane.** A vendor-supported client credential, service account or technical token must not be used by WFM if its effective authority is tenant-wide/super-admin or can impersonate arbitrary users. `superAdminCredentialAllowed:false` is fail-closed across the registry; the customer must provide a genuinely constrained identity or a customer-side read projection before tenant authentication can count as safe evidence.
- **Legacy OAuth grants are disabled for new WFM connectors.** Resource-owner password and implicit grants remain disabled (`oauthPasswordGrantEnabled:false`, `oauthImplicitGrantEnabled:false`). Prefer vendor-supported authorization-code/PKCE for delegated use or non-impersonating machine authentication tied to a least-privilege service identity; where a vendor offers user-bound public-key/JWT or short-lived token flows, validate their effective permissions rather than assuming the grant name is safe.
- **Known authentication/scope blockers stop evidence promotion.** When authoritative vendor evidence shows that the available integration path depends on a disabled authentication grant, super-admin/impersonation authority, unavoidable broad cross-scope read access or another unresolved security condition, record it as a `securityEvidenceBlockers` entry. A connector with unresolved blockers may be discovered, spec-verified and safely public-probed, but it must not be promoted to sandbox authentication, tenant authentication, read/write round-trip or production certification until a vendor-supported safe path or customer-controlled constrained projection resolves the blocker. The machine registry surfaces the blocker as the next evidence gate rather than pretending that successful login alone would be acceptable proof.
- **Permission labels are not permission proof.** Vendor roles named `limited`, `viewer`, `integration`, `operator` or similar must not be assumed read-only. Connector evidence must verify the actual allowed operations/endpoints and isolate technical credentials from any mutative management-plane capability before tenant authentication can count as safe WFM read evidence.
- **Management plane and data plane stay separate.** Industrial edge platforms can expose device onboarding, app deployment, configuration and control APIs alongside telemetry/data APIs. WFM should consume the minimum read-only data plane needed for workforce intelligence; management-plane operations require separate authorisation and evidence.
- **Broad and cross-scope reads are separately gated.** A channel is not safe merely because it is read-only. Bulk exports, notification streams, data lakes, analytics replicas or administrative query surfaces that can bypass the source system's object, device, site, entity or inventory RBAC remain disabled by default (`crossScopeReadEnabled:false`). They require a customer-approved constrained projection and separate evidence that effective scope is no broader than the intended WFM integration before they can be used.
- **Unauthenticated production data surfaces are disabled.** A vendor may expose anonymous, bearerless or authentication-optional APIs for convenience, interoperability, schema discovery, local testing or backwards compatibility. That does not make the surface acceptable for WFM production data. Business-data ingestion must remain disabled by default (`unauthenticatedDataSurfaceEnabled:false`) until the route is placed behind customer-approved authentication/authorization or an equivalent constrained gateway and tenant evidence proves scope, confidentiality and auditability. Public documentation/schema/help endpoints may still be probed without credentials when they contain no customer data.
- **Non-destructive messaging discovery.** Queue/topic discovery must use browse, mirror, tap, dedicated subscription or an explicitly authorised test queue where the platform supports it. A passive WFM connector must never destructively consume, acknowledge or remove an existing production message simply to prove connectivity. JMS/AMQP/Kafka adapters must preserve provider-specific acknowledgement, offset, transaction, selector, redelivery and dead-letter semantics.
- **Plant-network separation.** OPC UA, MQTT, BACnet and Modbus should normally terminate at a customer/site edge gateway. The cloud service should not scan production VLANs.
- **Authenticated OPC UA by default.** Production WFM must not rely on anonymous OPC UA even where a vendor exposes it for convenience. Endpoint identity, certificate trust, security mode/policy and the named technical identity must be customer-approved and validated before Browse/Read/Subscribe evidence is accepted; unknown or changed certificates must fail closed rather than be auto-trusted.
- **HTTPS does not remove the edge boundary.** An on-prem historian, MES, gateway or analytics service can expose REST/OData/gRPC over TLS while still being reachable only inside a plant or protected operations network. Vendor/system evidence may therefore set `customerEdgeRequired: true` independently of protocol family; the fabric must not invent an OPC/MQTT route just to trigger the edge guardrail.
- **Industrial data fabrics do not expand authority.** A historian, OT data fabric, secure tunnel, extractor or edge projection can reduce network exposure but does not make upstream data trustworthy for every purpose and does not grant WFM any extra rights. Use the minimum READ/LIST-style permissions, preserve source lineage and explicitly deny WRITE, MODIFY, function execution, device/configuration and control capabilities where the vendor separates them.
- **Derived analytics are not raw operational truth.** Historian views, calculated tags, OData exports, analytics platforms and digital-twin layers can filter, interpolate, aggregate, resample or otherwise transform source data. Preserve raw-versus-derived provenance, source/event time, ingestion time, quality/status, transformation or calculation identity and aggregation/window metadata. A derived or interpolated value must not silently masquerade as a live raw machine observation for labour, access, machine, process or safety actions.
- **Buffered data is not automatically current state.** Store-and-forward, offline edge caches and reconnect replay must retain source event time, ingestion time, source quality and site/source identity. Late or stale observations may update reconciled history but must not silently trigger real-time labour, door/access, machine, process or safety actions as though they were live.
- **Industrial control writes are separately gated.** The existence of an OPC UA/MQTT/REST write or method-call capability does not permit WFM to use it. Machine, PLC, BMS, door/access and safety-system control requires an explicit business case, customer authorisation, sandbox/site test, rollback design and a separate production safety review.
- **Data minimisation.** Canonical mapping should ingest only fields needed for workforce, production, cost, compliance and decision workflows. Category-derived opportunity profiles are planning hypotheses and must not be used to justify collecting fields that the implemented workflow does not require.
- **Sensitive workforce segregation.** Payroll, identity, access-control and authentication-event data require narrower scopes and retention than general production telemetry. Correlation should prefer stable pseudonymous worker keys over copying unnecessary personal data.
- **Learning evidence is not automatic work eligibility.** Course completion, certificates and competency scores may support a customer-defined qualification rule, but the source record must not automatically grant or revoke job eligibility unless the customer has explicitly mapped that evidence to the role/skill requirement and the rule is auditable.
- **EHS and health-sensitive data require minimisation by design.** Safety systems can contain incident narratives, investigation material, medical information and other highly sensitive records. WFM should normally ingest only a derived eligibility/restriction, incident classification or risk signal needed for the workflow—not the underlying sensitive record. Any health-related or special-category data requires a separately justified, authorised and retention-controlled design.
- **Replay/idempotency.** Webhooks, files and event streams require a source event ID or deterministic dedupe key.
- **Rate limits.** Each vendor adapter must honour vendor-specific throttling and Retry-After semantics.
- **Version drift.** API versions and schema fingerprints are evidence inputs; a changed contract degrades the connector until compatibility is re-proven.
- **Tenant isolation.** Connection configuration and tokens are scoped to one customer tenant/site boundary and never reused between customers.
- **Regional routing.** Where vendors expose region-specific endpoints, the connector must bind the tenant to the configured region and must not silently fail over across data-residency boundaries.
- **Vendor host migrations and rebrands fail closed.** A vendor rename, API-host transition, vanity domain, redirect or documented legacy alias does not authorise the connector to follow a new hostname automatically. Cross-host redirects remain disabled by default (`crossHostRedirectAllowed:false`). The new host or alias must be vendor-documented or customer-approved, reviewed for data-residency and authentication changes, and explicitly pinned before use; the old and new hosts must not be treated as interchangeable tenant boundaries merely because both currently respond.
- **Diagnostic redaction.** Logs may include connector ID, status, latency and correlation IDs, but not reusable credentials or raw sensitive payloads.
