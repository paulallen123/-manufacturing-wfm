# Synthetic leave proof action: authority blocker and test-only contract

No hosted business action is authorized by this packet. The signed browser runner remains exactly its existing navigation-only source; leave, attendance and payroll business journeys remain unproved. The executable contract and SQLite transactions below are local models using generated keys and fictional records. They have no production imports, issuer, protected configuration, new endpoint or deployed hook.

## Exact source and ownership

The inspected product source is PR501 commit `61718e1862fa650136e1952f622c9d8dd4c22af8`. The unchanged runner Git blob is `b736e153d621daeec4915fbe8627885b6496ff00`, SHA256 `5d5921f54b3e501f70004d324036e3c5fbd336b1f04550cb0ec390434252d903`.

- `security/runtime/proof-runner-auth.cjs` signs email, origin, nonce and timestamps. It resolves tenant/role from stored users, serializes issuance against identity changes, records issuance durably, and rejects nonce replay. This authenticates a principal; it does not approve a leave action or bind its request, source, implementation run or configuration.
- `security/runtime/identity-survival-guard.cjs` contains proof sessions when stored email/tenant/role or expiry changes. This remains necessary identity enforcement; it is not per-action approval.
- `scripts/current-candidate-role-browser-proof.mjs` requires explicit actors and source/deployment/tenant/run/configuration context, then the signed branch returns `PARTIAL`, `signed-auth-navigation-only`, and null business journeys. These inputs cannot create approval.
- `operations/runtime/autopilot-execution-engine.cjs` has durable human permits, but explicitly permits only `OVERTIME_OVERRIDE` and `AGENCY_ASSIGNMENT` through its workforce adapter. It has no leave approval contract. Reusing or broadening it would be a separate product change requiring review.
- Policy source registries and policy graphs explicitly set execution authority to false. A policy source reference is not an execution grant.
- The current UX posts `leave-decision` to `/api/command` with the request ID, decision, reviewed flag and state version. No protected proof grant is checked or consumed by that existing boundary.

Issue [#527](https://github.com/paulallen123/-manufacturing-wfm/issues/527) preserves one canonical PR501 integration/release owner, the existing secure operator/proof owner for protected binding, and coordinator-only reconciliation of shared lane state. Its proof pool forbids self-approval and production/provider writes. This packet is an isolated documentation/test handoff on existing PR528; it does not replace those owners or change any shared lane completion flag.

## Missing authority: the concrete unblock input

An owner must provide an independently governed approval issuer and durable, trustworthy synthetic fixture provenance. Neither exists for a leave proof action in the inspected source. An environment JSON object containing `synthetic:true` and an approval reference is runner self-assertion. A second key generated by the runner would also be self-approval. Keys generated in these tests authorize only the local fictional model.

Before any runtime integration, the existing secure operator and integration owner must establish all of the following through their protected approval process:

1. A real issuer policy identifying who can approve this one synthetic action, how the issuer authenticates that authority, where approval/revocation records are held, and how those records are audited. The authority must be independent of the proof login signer and runner. The approval public key must be registered by that policy; the runner must never select its own trusted key or supply the protected record.
2. A server-held fixture/cohort record establishing that this exact tenant, employee and pending request are fictional, together with its immutable provenance digest. A fixture-only health response alone does not prove that every pending request is synthetic. Customer/provider operations must remain disabled by authoritative policy.
3. One current protected approval record binding the exact canonical grant digest, reference, APPROVED state, revocation state and expiry. All approval and business context must be read from authoritative server state under the command transaction lock. Client JSON, environment variables, an earlier GET response or a supplied context snapshot cannot substitute.
4. An owner-reviewed adapter at the actual `/api/command` boundary which validates and consumes the grant atomically with the version-checked leave decision and append-only business audit. Existing native manager/reporting-chain rules and session containment still apply. A client-only preflight does not enforce this contract.

These are external authority and integration prerequisites, not values this packet creates. No grant or approval request for a real actor/request is included.

## Bounded contract modeled by the tests

The contract uses a distinct Ed25519 approval key and a complete, fixed-order JSON signature domain. It rejects unknown or missing fields, ambiguous encodings, non-finite numbers and mismatched context. Its signed claims include:

| Binding | Required scope |
| --- | --- |
| Purpose | Schema, issuer, audience, `approve-synthetic-leave`, decision `approved` |
| Approval | Unique grant ID and protected approval-record ID |
| Time | Safe integer issued/expiry times, no future issuance, strict expiry with no skew, lifetime at most 30 minutes |
| Deployment | Exact HTTPS origin, source SHA, deployment ID |
| Implementation | Exact tenant, implementation run and configuration digest |
| Principals | Exact normalized manager/employee emails and persisted person IDs; no self-review |
| Synthetic provenance | Exact server-held fixture ID and provenance digest |
| Business request | Exact pending leave ID/date/hours/period and current state version |

Current server context must independently match every scope field. It must contain the active proof manager session, current native review permission, a pending synthetic request, fixture-only state, production-unapproved state, and disabled customer/provider actions. It must also contain the exact current protected approval ID/digest, APPROVED/nonrevoked state and matching expiry. Missing evidence refuses the local model.

The proof contract deliberately narrows hours to 0.5–12 with whole minutes. The current UX accepts 0.5–12 and rounds to minutes; whole-minute input is a narrower proposed proof policy. This packet does not change native leave validation.

`verifyGrant` is a pure test-only checker. Repeated successful verification is not grant consumption, and its result is explicitly `productionReady:false`. It is not an HTTP allow token or production API. Its context argument exists to exercise the contract; there is no current trustworthy application adapter producing that context.

The primary SQLite fixture, independently exercised by the heldouts, demonstrates the required transaction: `BEGIN IMMEDIATE`, reload protected approval plus identity/request/configuration context, check signature and time immediately before synchronous writes, insert unique consumption, compare-and-set the pending request version, append exact audit, then commit. A thrown audit operation rolls back all local writes. A committed response-loss retry cannot repeat the decision. A newly issued grant for a stale request version also fails. The fixture exercises SQL state only; it does not call the app, a provider, browser or hosted service.

Any future adapter must use that same authoritative business database/transaction and hold approval/revocation/configuration invariants until commit. No awaited browser/network work may occur between validation and mutation. If the actual command requires another datastore or an external side effect, this local transaction design is insufficient: the owner must provide durable intent, unique dispatch and uncertain-result reconciliation first. An uncertain external result must not renew/replay the action. Business readback after commit proves what happened; it cannot grant retroactive approval.

## Validation and claim limits

The packet retains the builder's existing 50/50 auth/server/wrapper tests and independent 24/24 checks on both baseline and restored runner, all on Node 22.23.2. These prove local source/contract behavior only. A rejected, unpublished env-only prototype produced one simulated UI submission when the independent local seam expected zero. Its unsafe source and prototype-only test remain unpublished; its failure receipt is retained solely to explain why no runtime hook was adopted. The rejected prototype is not the published product and was never activated; that counterexample does not establish a current product vulnerability or a hosted write. All of those checks used local fictional responses, not customer actions.

The new contract's review-red receipt records six failures before protected-record and hours/version tightening. Its final primary suite and independent heldouts are recorded separately in `manifest.json`; they must not be added to hosted customer acceptance counts.
