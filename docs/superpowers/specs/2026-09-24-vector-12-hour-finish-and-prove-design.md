# VECTOR 12-Hour Finish-and-Prove Design

Date: 24 September 2026  
Canonical product line: `feature/vector-eow-convergence-20260925`  
Release principle: no waiver, no claim inflation, no simulation counted as operational proof, no unsafe shortcut.

## Intent

Finish the currently planned VECTOR/FORGE programme at a higher engineering and proof standard, without weakening any existing ambition, changing the approved blue-and-white role-first FORGE experience, reviving retired UI, creating a parallel T9 product, coupling Northstar into VECTOR production control, or trading security/payroll/tenant-isolation controls for speed.

The output is customer-ready only where the exact candidate is demonstrably working end to end and the evidence survives independent verification.

## Non-negotiable success criteria

A capability is not complete because source exists or unit tests pass. Every claimed-delivered capability must reach:

1. exact source/build provenance;
2. deterministic positive tests;
3. negative/security tests;
4. hosted authenticated role/tenant journey;
5. consequential action or explicit safe abstention;
6. independent postcondition verification;
7. persistence after refresh/new login;
8. restart/recovery and replay safety;
9. rollback/compensation or fail-closed containment;
10. destructive fault test;
11. evidence/decision receipt bound to immutable release identity;
12. regression generated from verified failure/outcome;
13. canary/shadow evidence where relevant;
14. independent promotion.

No simulated or fixture-only evidence may be represented as production/customer proof.

## Scope retained

The programme preserves and converges all currently committed domains, including:

- approved FORGE Today / People / Plan / Improve experience;

- Factory Autopilot and verified bounded action;

- value proof;
- adaptive/self-learning under independent promotion control;
- autonomous support/recovery;

- release governance and proof.

The existing T9 Sunday exit contract remains additive and authoritative for T9 claim boundaries.

## Operating architecture

### 1. One canonical release graph

Every requirement maps to a machine-verifiable release gate. Work may occur in isolated proof lanes, but product capability converges into the canonical FORGE release path. No independent feature branch may become a second product architecture.

### 2. Parallel worker topology

Capacity is split by responsibility, not duplicated writing:

- build workers: implement/fix clearly partitioned subsystems;
- integration workers: converge interfaces and exact candidate packaging;
- adversarial workers: attempt to break each capability;
- security/recovery workers: tenant, payroll, identity, rollback, restart and fail-closed testing;
- proof workers: hosted browser/API/data/persistence evidence;
- performance workers: latency, throughput, concurrency and 10,000+ employee / multi-site scale;
- release guardians: prevent architecture/UI/security drift;
- one canonical orchestrator: owns dependency graph, claim ledger and promotion state.

A builder cannot certify its own work.

### 3. Northstar isolation

Northstar remains a separate test/simulation environment. It may assault VECTOR with realistic scenarios and external-system emulation, but it receives no authority over production VECTOR and shares no production trust boundary.

### 4. Evidence spine

Every consequential flow should bind:

UI action -> authenticated actor/tenant -> API/request -> business rule -> authoritative mutation -> persisted state -> audit/evidence record -> returned state -> refreshed UI -> verifier postcondition -> recovery/rollback result -> release identity.

Customer-ready claims require this chain, not screenshots alone.

## Twelve-hour execution sequence

### H0-H1: Release delta and proof census

- resolve exact canonical heads and active deployments;
- inventory planned capabilities against current evidence;
- mark each domain BUILT / EXACT-CANDIDATE / HOSTED / ACTION-PROVED / VERIFIED / RECOVERY-PROVED / CUSTOMER-READY;
- identify proof gaps and dependency order;
- freeze non-release-critical novelty.

### H1-H4: Parallel repair and completion

- clear existing deterministic test failures;
- finish missing persistence/read-back paths;
- converge T9 trust/assurance into the canonical FORGE path without a separate product branch;
- repair integration metadata/evidence drift;
- close UI-to-backend-to-persistent-state gaps;
- generate regression tests for every verified defect.

### H4-H7: Canonical convergence

Continuously run the Golden Journey against the exact candidate:

contract/tenant -> integration discovery -> import/reconciliation -> configuration -> training -> go-live -> scheduling -> clock/absence -> manager approval -> payroll/downstream update -> realised value evidence -> injected failure -> detection -> repair/rollback -> verified outcome.

No domain is promoted because an isolated test service passes.

### H7-H9: Compound destructive assault

Run multi-domain fault combinations including:

- stale/contradictory data;
- lost write acknowledgement;
- restart mid-action;
- rollback failure;
- cross-tenant injection;
- identity provider outage;
- telemetry blackout;
- schema drift;
- no upstream system;
- device/edge offline;
- payroll deadline with unresolved evidence;
- model/agent unavailable;
- poisoned prompt/memory;
- regional outage;
- customer correction;
- unknown cascading failure.

### H9-H11: Failure burn-down

Every failure follows:

reproduce -> isolate cause -> implement fix -> focused test -> destructive retest -> wider regression -> exact candidate -> hosted verification -> evidence binding.

No failed gate is hidden or reclassified.

### H11-H12: Independent release attempt

A clean verifier, not the implementing workers, runs the complete customer path on the exact hosted candidate. Customer-ready status is awarded only to capabilities with retained evidence.

## Performance and customer-readiness gates

Minimum evidence set:

- exact immutable source/build identity;
- full deterministic suite green for candidate-relevant tests;
- hosted health and authenticated functional proof;
- role and tenant isolation proof;
- no direct consequential-write bypass;
- idempotency/replay proof;
- rollback/compensation proof;
- restart/recovery proof;
- persistence after refresh/new login;
- 10,000+ employee / multi-site scale evidence where applicable;
- latency/throughput evidence for critical workflows;
- browser-level proof of approved FORGE UI;
- no retired presentation assets in active runtime;
- customer data / production mutation boundary explicitly proven;
- external providers distinguished as live-proven, sandbox-proven, simulated, or unproven;
- no claim of realised financial value without reconciled outcome evidence.

## Evolution rule

The programme may improve VECTOR beyond the current plan only when the improvement:

1. increases customer value, autonomy, usability, reliability, performance, security or proof quality;
2. is additive to existing ambition;
3. does not destabilise the release path;
4. can be independently tested;
5. does not expand authority without evidence.

Interesting ideas without release-critical value are captured but do not interrupt the twelve-hour convergence path.

## Claim ledger

Each domain must end in one explicit state:

- UNPROVEN
- BUILT
- EXACT_CANDIDATE_TESTED
- HOSTED_SHADOW_PROVED
- BOUNDED_ACTION_PROVED
- OUTCOME_VERIFIED
- RECOVERY_PROVED
- CUSTOMER_READY

No percentage may substitute for missing evidence.

## Hourly reporting

Each update reports:

- newly completed + proven capability;
- exact evidence gathered;
- current failures/unproven items;
- customer-ready status by major domain;
- performance/security/recovery evidence;
- blockers and resolution/alternate route;
- highest-priority next-hour work.

If no new proof exists, the update states that explicitly.

## Exit condition

The twelve-hour push is successful only if the exact canonical candidate can be shown, not merely described, performing the planned customer workflows with independent proof and recovery evidence.

If engineering reality disproves a capability, the capability remains unproven until fixed and retested. The deadline never weakens the claim standard.
