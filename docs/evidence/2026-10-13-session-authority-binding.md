# Bound session authority after role or permission changes

- **Requirement/source:** Issue #265 security lane requires a permission-revocation race check and session/token revocation proof. This package addresses the narrower server-side gap where a session already admitted by `identity-survival-guard.cjs` continued through later requests after its user's role or permission record changed. It does not close an in-flight mutation between admission and an action's commit.

- **Result:** On initial session binding, store a digest of the current role and permission text in a separate SQLite table. Later requests compare current authority to that snapshot and revoke the presented session on mismatch. Existing password bindings without a snapshot require fresh login. Existing passkey/signed-proof issuance paths pre-bind their sessions; sessions issued after this guard generation can acquire the new snapshot at first guarded request after the existing role/issuer/scope checks. Older pre-bound sessions require fresh login. No user permission, payroll, or tenant record was changed outside synthetic tests.
