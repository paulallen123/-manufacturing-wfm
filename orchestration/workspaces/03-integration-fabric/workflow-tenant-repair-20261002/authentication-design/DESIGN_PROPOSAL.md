## Actual blocker and canonical routes

The historical workflow explicitly runs local Docker with WFM_HOSTED_STAGING=true and then expects POST /api/login200. Exact bootstrap enables passkeyAuth for hosted, intercepts /api/login with410, and cannot provide the password fallback. Docker's existing NODE_ENV=staging and identity-survival enforcement are source declarations, not demonstrated container execution. The whole workflow is blocked before the isolated tenant fix. The original repaired variable defect is independently tracked as WORKFLOW-TENANT-01 and corrected in a separate reviewed successor; none of its source or seals were changed here.

Two existing authentication paths can create authority-backed session rows:

* POST /api/proof-runner/session (canonical source0165b9a5207eeb870e2690c4da6456ec8457db7e) accepts an Ed25519 assertion only when explicitly enabled in hosted staging, with NODE_ENV=staging, WFM_DB, HTTPS public origin, an Ed25519 public key and explicit email allowlist. It validates transport/request origin, assertion origin, lifetime, nonce and signature; looks up the current persisted user; commits a one-use nonce, session, scope metadata and durable audit atomically; returns secure HttpOnly SameSite=Strict wfm_session cookie and actor from that user. Client tenant/role never supplies authority. Invalid/replayed assertions, missing current user, failed durable audit or a preexisting session fail closed.
* Existing passkey authenticate/options + authenticate/verify requires a registered current credential, origin/RP/challenge, user handle and cryptographic user verification. Registration requires a valid existing identity-bound session or a current single-use recipient-bound invitation. Existing passkey test fixtures generate and sign real WebAuthn transcripts, but directly seed proof-session rows for fixture enrollment; that setup is not an authorized deployed-caller entry path. There is no legitimate cookie/credential/invitation default available in this workflow.

Identity-survival guard remains before proof-runner exchange and rejects injected authority headers. Existing issued proof/passkey sessions must still match persisted user tenant/role, session epoch, policy and privileged freeze before reaching authenticated bootstrap or hub managers. No future caller should bypass, disable or mint those bindings directly.

## Narrow compatible future caller design

Prefer the already canonical signed proof-runner exchange for an explicitly configured headless staging proof, conditional on root verifying the existing authorized signer and server allowlist/configuration. Reuse exported canonicalAssertion and the canonical constants, not another signer format/auth handler. Obtain a short-lived assertion for the exact existing manager@northstar.example identity from its authorized signing boundary; sign the exact configured canonical HTTPS origin, fresh cryptographically generated nonce, and bounded issued/expires times. Send no existing session cookie and no identity-injection headers; use existing declared origin/routing parameters. Accept only a successful secure session issuance, then use that cookie for existing /api/bootstrap and require exact manager email/role plus bounded tenant before any integration mutation. Keep the isolated tenant validator and canonical manager/current tenant fences intact. A superuser proof identity cannot be silently substituted to satisfy a missing manager allowlist.

No new auth authority, cookie/session row writes, enrollment shortcut, invitation default, worker credential reinterpretation, broad authorization, session ledger or automatic retry is proposed. Replay and ambiguous issuance must remain fail closed; proof authentication is not a generic autonomous retry target. Passkey is the supported customer path when a legitimately registered device and user verification are available; using the isolated test authenticator to impersonate a missing deployed credential is rejected.

## Explicit prerequisite gaps

Local workflow does not enable WFM_PROOF_RUNNER_AUTH or provide a public key/email allowlist. Therefore swapping the endpoint alone cannot make it work. Enabling a dedicated ephemeral isolated proof fixture using the existing canonical module would require a separate root-approved future workflow/configuration delta and isolated admission; it is not implemented or presumed authorized here. No operational signing key is generated or persisted; unchanged canonical tests generate synthetic ephemeral keys in memory. Existing hosted configuration/allowlist/signer access were not fetched and remain unknown. A live signing source, manager permission and exact origin must be independently verified; module presence does not establish them. Hosted service metadata/name does not establish authentication availability.

Without those prerequisites, return BLOCKED_EXTERNAL/CONFIGURATION_PREREQUISITE for assembled workflow admission instead of changing handlers or disabling security. Root owns the authentication design decision and any existing proof-runner coordination. This Lane03 work only proposes a caller reuse path; canonical security modules retain their existing owners and bytes.
